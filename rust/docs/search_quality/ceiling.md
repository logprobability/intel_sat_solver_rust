# Oracle ceiling: does accurate advice help the search?

Before building anything that *predicts* advice for the solver (phases from a model of a similar instance, scores from a previous run, a learnt predictor),
this experiment measures the most that such advice could buy: the advice is taken from the answer itself.

* **Phase oracle**: an instance is solved once; its model is then given back as phase hints (`/phase/hints/on 1`, `/topor_tool/hints_file`), correct for a fraction `p`
  of the variables, and the instance is solved again. The other variables are hinted the *opposite* polarity ("flip": a predictor which is confidently wrong)
  or aren't hinted ("none": a predictor which abstains). 5 random choices of the variables per `p`; the tables hold the median.
* **Family oracle**: a `planner_*` instance is hinted the final phases of a *different* `planner_*` instance (the variables of the same index).
* **Carry-over**: an instance is solved again with what its own first run has written (`/topor_tool/write_hints_file`): the ranks of the final decision scores
  (`/decision/score_hints/mult M`), the final saved phases, or both. For an unsatisfiable instance there is no other advice to give.
* **Control**: the same score hints, randomly permuted among the variables: advice without information, which only perturbs the decision order.

Search quality is measured in **conflicts** (cumulative over the queries of an instance); decisions and CPU time are secondary.
The full tables are in [`ceiling_tables.md`](ceiling_tables.md), generated by `scripts/phase_oracle_ceiling.py` (about 6 minutes; 5740 runs over 104 instances, 79 of them satisfiable).
Every model was verified by the tool, and no run contradicted another one (SAT versus UNSAT), whatever the hints: wrong advice only costs time.

## The instances, and what they can show

* The 78 regression instances. All but the four `planner_*` ones are trivial (at most 129 conflicts, 383 in total), so they show nothing either way.
* The four `planner_*` instances are recorded *sequences* of queries of the satdb join planner, and two things about them matter here:
  the planner already fixes the polarity of practically every variable with `lf` (`FixPolarity`, which takes precedence over a hint), and most of their conflicts are spent
  in queries which a model cannot help. The conflicts per query of the recorded runs:

  | instance | queries (verdict: conflicts) |
  |---|---|
  | planner_constraint_cores | UNSAT: 0, SAT: 15, SAT: 25, SAT: 29, final SAT: 0 |
  | planner_huge_budget | CONFLICT_OUT: 1, CONFLICT_OUT: 1, UNSAT: 7507, final SAT: 53 |
  | planner_large_query | CONFLICT_OUT: 1000, CONFLICT_OUT: 10000, final SAT: 3926 |
  | planner_small_refinements | 100 x CONFLICT_OUT: 1, final SAT: 6613 |

  The final query of each sequence (no assumptions, no threshold) was appended for the regression suite; it is not a query of the planner. Without their thresholds,
  the first three queries of `planner_huge_budget` are unsatisfiable, and the first query of `planner_large_query` doesn't finish in 150 seconds.
* To isolate the effects, three versions of each planner instance are derived: `.nolf` (the recorded queries without the `lf` commands), and two single-query ones:
  `.lf` (the clauses and the `lf` commands) and `.plain` (the clauses only).
* Since nothing above is a hard satisfiable query, 6 satisfiable uniform random 3-SAT formulas (200 variables, ratio 4.1; 387 to 12826 conflicts) are generated for the phase oracle,
  and 6 unsatisfiable ones (175 variables, ratio 4.7) and 2 pigeonhole formulas (3043 to 14052 conflicts) for the carry-over.

## Reading

1. **The ceiling of phase advice on a single satisfiable query is total, and it degrades gracefully.** With the model as hints, every single-query instance without `lf`
   is solved with 0 conflicts (necessarily: all the decisions agree with a model, so BCP cannot conflict).
   On random 3-SAT, where the control shows that the gain isn't a matter of luck (random perturbation: 1.25), correct hints for half of the variables already give
   0.36 of the conflicts, for three quarters 0.07, and for 95% 0.002.
2. **Abstaining beats guessing.** If the other variables are hinted wrongly, 50% accuracy is worthless (1.37), 75% is marginal (0.82), and the large gains start at about 90% (0.18; 0.02 at 95%).
   A predictor is worth building only if it is right on some 90% of the variables it speaks about, and it should stay silent about the rest.
   Fully wrong advice costs 1.14x on average and up to 3x on an instance (387 -> 1162 conflicts) in these runs, and never an answer.
3. **For the planner workload as recorded, phase advice has no measurable headroom.**
   * In the recorded instances the hints change next to nothing (the medians move by at most 4% for any `p`): the planner's `lf` fixes the polarities, and a fixed polarity wins over a hint.
   * Dropping `lf` doesn't uncover a gain in the planner's own queries either: they are unsatisfiable or run out of their conflict budgets (the table of the queries above), and no model exists to advise them.
     The 0.601 marked (*) is not a gain: in `planner_huge_budget.nolf` the hints shift the conflict counts of the first two queries, after which the conflict threshold of the third one, just below the maximal `uint64_t`,
     wraps around when it is added to the number of conflicts so far (as in the C++ solver), and the query is cut off instead of being refuted.
   * Only the appended final query is satisfiable, and there the oracle does reach its ceiling, but only if `lf` is out of the way *and* the hints are given again right before the query:
     hinted once before the first query, the model is overwritten by phase saving during the earlier queries (`planner_large_query.nolf`: 14466 -> 15241 conflicts),
     hinted before every query, the final query takes 0 conflicts (14466 -> 11004, which is the two conflict budgets; `planner_small_refinements.nolf`: 5062 -> 136).
     With `lf` in force, even that barely helps (14926 -> 12656, 6724 -> 6600, 7562 -> 7667). In incremental use a hint has to be renewed per query.
   * **The base runs of the planner's final queries are not a trustworthy reference.** On the clause-only single queries, 39 of 45 runs with *random* score hints take 0 conflicts
     (all 15 for two of the three instances), where the base runs take 2372, 4961 and 4412; on `planner_large_query.plain`, a single `lb` (BoostScore) of an arbitrary variable does the same with the unmodified solver.
     With `lf` in force, the random perturbation (0.297) is as good as the oracle (0.285). These queries are easy, and the default decision order happens to be a bad one for them,
     so on the planner instances an apparent gain of *any* advice over the base run must be compared with the control before it is believed.
     (The same comparison says that the planner's `lf` costs conflicts on these final queries: 16 to 3752 with it under perturbation, 0 without it. Whether that holds for the planner's real queries, the data cannot tell.)
4. **Family advice by variable index doesn't transfer reliably.** In the recorded instances it changes nothing (`lf`). In the single-query versions it sometimes helps
   (`planner_huge_budget.plain`: 2372 -> 66 with the phases of `planner_large_query`; `planner_large_query.plain`: 4961 -> 379 with those of `planner_small_refinements`),
   but those are the instances which random perturbation already brings to 0, and with `lf` in force it can hurt by up to 3.5x (`planner_small_refinements.lf`: 2939 -> 10394; `planner_large_query.lf`: 4581 -> 9584).
   The same index means different things in different planner queries; carrying phases over needs a mapping by meaning, which the planner has and the solver doesn't.
5. **Score carry-over is real on unsatisfiable instances, and modest.** Re-solving the *same* unsatisfiable instance with the final score ranks of the previous run takes 0.92 / 0.79 / 0.75 of the conflicts
   (mult 1 / 10 / 100; at 100 each of the 8 instances gains, 0.66 to 0.91), while the same scores permuted at random do nothing (1.01 to 1.04). The final phases of an unsatisfiable run don't help (1.05).
   This is an upper bound for carry-over between *similar* instances. On the satisfiable instances the carried scores are indistinguishable from random ones (0.22 to 0.24 either way),
   and on the recorded planner sequences they are within the (large) noise of the control: 7562 -> 6442..6818 (control: 5911..7299), 14926 -> 16829..21398 (14363..17043), 6724 -> 9787..12658 (7237..9887).
6. **Decisions and time.** Decisions fall with the conflicts, but less (0.14 of the base at p=1: every variable which isn't implied still takes a decision).
   The CPU time ratios are all between 0.95 and 1.01 and say nothing: these runs take a fraction of a second, much of it reading the input.

## Bottom line

* Accurate phase advice is worth a lot on a hard satisfiable query (random 3-SAT: 14x fewer conflicts with correct hints for 75% of the variables and silence about the rest), and it is harmless when wrong
  only in the sense of soundness: below about 90% accuracy a predictor which doesn't abstain gains little or loses.
* For the planner, this experiment finds no use for phase advice beyond what `lf` already does: the conflicts of its queries are in refutations and exhausted budgets.
  The advice which applies there is about the decision *order* (scores), where the carry-over ceiling on identical unsatisfiable instances is 20 to 25% of the conflicts,
  and the larger and cheaper effect seen here is the sensitivity of the planner instances to the decision order itself.
* The evidence is thin: four planner recordings, whose final queries are artificial, and 14 generated formulas. The numbers are medians of 5 seeds, and single runs vary by factors (see the control columns).
